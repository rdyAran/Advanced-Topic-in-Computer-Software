# FloodLink 🌊

**ศูนย์ประสานงานร่วม รัฐ × อาสา ช่วงน้ำท่วม ที่มีโมเดล AI ของทีมเองเป็นแกน**

ระบบนี้รับข้อความขอความช่วยเหลือจากทุกช่องทาง (Facebook / LINE / โทรศัพท์ / Traffy Fondue) แล้ว**โมเดลที่ทีมเทรนเอง**จะแยกประเภทข้อความและดึงข้อมูลออกมา จากนั้นระบบจะให้สีตามเกณฑ์ ปภ. รวมเคสซ้ำ และแสดงผลบน dashboard ที่รัฐกับอาสาเห็นร่วมกัน

ถ้าโมเดลของเรา**ไม่มั่นใจ**ในข้อความไหน Agent จะส่งข้อความนั้นต่อให้ LLM (Gemini) อ่าน แล้วนำคำตอบของ Gemini กลับมาเป็นข้อมูลเทรนรอบถัดไป ทำให้โมเดลของเราเก่งขึ้นเรื่อย ๆ

## ขอบเขตโปรเจกต์ (v0.16)

**ธง:** FloodLink รับเรื่องขอความช่วยเหลือช่วงน้ำท่วมจากผู้ประสบภัยผ่านมือถือ ใช้ AI ของเราเองคัดแยกและจัดลำดับความเร่งด่วน แล้วส่งต่อให้ศูนย์ประสานงานมอบหมายทีมกู้ภัยจนปิดเคสได้ (สถานการณ์สาธิต: หาดใหญ่)

| ระดับ | ใคร | เข้าระบบ | ทำได้ | ทำไม่ได้ |
|---|---|---|---|---|
| ผู้แจ้ง | ผู้ประสบภัย, ญาติ, อาสาที่ฝากเคส | ไม่ต้องล็อกอิน · ได้**ลิงก์ติดตามส่วนตัว** `/track/<token>` | ส่งข้อความ/รูป/พิกัด · ดูสถานะและประวัติเคส · ส่งข้อมูลเพิ่ม · กด "ปลอดภัยแล้ว" | เห็นเคสคนอื่น |
| หัวหน้าชุด (`rescuer`) | 1 บัญชีต่อ 1 ชุด: เรือ อาสา มูลนิธิ หน่วยงานรัฐ (ประสานลูกทีมเอง) | ล็อกอิน (ศูนย์สร้างบัญชีให้) | เห็น**เฉพาะเคสของชุด** · **รับเคส / ไปไม่ได้ (พร้อมเหตุผล)** · ขอรับเคสใกล้ตัวที่ยังไม่มีชุด · ตั้งสถานะชุด ว่าง/กำลังช่วย/พัก · ส่งตำแหน่งชุด · เรือ/ที่นั่ง/พยาบาล · ปิดเคส (ช่วยแล้ว/ไม่พบ) · บันทึก+รูป · แจ้งเตือนงานใหม่ | เปลี่ยนสี · เห็นเคสชุดอื่น · เห็นเบอร์/บ้านเลขที่ก่อนรับเคส |
| เจ้าหน้าที่ศูนย์ (`coordinator`) | ปภ., เทศบาล | ล็อกอิน | **สร้าง/ปิดบัญชีหัวหน้าชุด** · กระดานชุด (สถานะ ตำแหน่ง ความจุ งานที่ถือ) · ระบบแนะนำชุด (ว่าง → ใกล้ → มีพยาบาลถ้ามีผู้ป่วย) · เตือนเมื่อชุดไม่ตอบรับเกิน 10 นาที · คิวทั้งหมด · ตรวจเคส · มอบหมายทีม · ปิดเคส 4 แบบ · เปิดเคสใหม่ · **แก้ผล AI** · รับเรื่องทางโทรศัพท์ · ดูประวัติเคส | จัดการบัญชี |
| ผู้ดูแลระบบ (`admin`) | ทีมเรา | ล็อกอิน | ทุกอย่างข้างบน + บัญชีผู้ใช้ · เดโม/ล้างข้อมูล · audit log · export ข้อมูลเทรน | — |
| สาธารณะ | ทุกคน | — | `/public` ตัวเลขสรุป รายพื้นที่ แผนที่แบบหยาบ (ปัดพิกัด ~1 กม.) | เห็นชื่อ เบอร์ ที่อยู่ ข้อความ รูป |

**วงจรเคส:** ใหม่ → ตรวจแล้ว → มีทีมรับ → กำลังช่วย → **ปิดเคส** (ช่วยแล้ว / เคสซ้ำ / ไปแล้วไม่พบ / ปลอดภัยเอง) — ทุกการเปลี่ยนแปลงลง audit log ว่าใครทำอะไรเมื่อไหร่

**บัญชีเดโม** (สร้างตอนเปิดครั้งแรก): `admin`, `officer`, `boat1` (ทีมเรือ 1), `boat2` (ทีมเรือ 2) รหัสผ่าน = `SEED_PASSWORD` ใน `.env` (ถ้าเว้นว่าง ระบบสุ่มให้แล้วพิมพ์ใน `docker compose logs api`) · หน้าเจ้าหน้าที่: http://localhost:5173/staff

**ความเป็นส่วนตัว:** รหัสผ่าน PBKDF2 · session เป็น cookie HttpOnly ที่เซ็นด้วย HMAC (เปลี่ยนรหัส/ปิดบัญชี = หลุดทุกเครื่อง) · ล็อกชั่วคราวเมื่อใส่รหัสผิด 5 ครั้ง · รูปเปิดได้เฉพาะเจ้าหน้าที่ ทีมที่รับเคส และผู้แจ้งเจ้าของรูป · แชทบอทตอบสถานะเคสจากเลขเคสแบบไม่มีที่อยู่/รายละเอียด

**นอกขอบเขต:** เชื่อม LINE ของจริง · SMS/OTP · แอปติดตั้ง · เชื่อมระบบราชการจริง · หลายจังหวัด · จับคู่ผู้บริจาค · ใช้ข้อมูลกลุ่ม LINE ที่ไม่ได้รับอนุญาต

## สคริปต์สาธิต (ประมาณ 7 นาที)

เตรียมก่อน: `.env` ตั้ง `SEED_PASSWORD` → `docker compose up -d` → เข้า `/staff` ล็อกอิน `admin` → เมนู ⋯ → **โหลดข้อมูลเดโม** (ได้เคส 40 เคส ชุดเรือ 2 ชุดมีตำแหน่ง มีเคสกำลังช่วย 1 รอตอบรับ 1 ตรวจแล้ว 2)
เปิดหน้าจอ 2 จอ: คอม = ศูนย์ (`officer`), มือถือ = หัวหน้าชุด (`boat1`) — มือถือเข้า `http://<IP คอม>:5173` ต่อ Wi-Fi เดียวกัน

1. **ผู้ประสบภัย (มือถือ ไม่ล็อกอิน):** หน้าแรก → พิมพ์ "ยายติดเตียง น้ำถึงชั้น 2 ซ.คลองแห 2" + แนบรูป → ส่ง → ได้ลิงก์ติดตาม → เปิด เห็นเช็กลิสต์ว่ายังขาดเบอร์ → ส่งเบอร์เพิ่ม → ข้อมูลครบ
2. **ศูนย์ (คอม):** เสียงเตือน + แถบแดง "เคสแดงใหม่" → กด **ดู C-xxx** เลื่อนไปที่เคส → เห็นเหตุผลที่ได้สีแดง ข้อความต้นฉบับ AI อ่านได้ว่าอะไร → **✓ ตรวจแล้ว** → **มอบหมายชุด** เลือกตัวที่มี ⭐ แนะนำ (ว่าง · ใกล้ · มีพยาบาล)
3. **หัวหน้าชุด (มือถือ):** เสียงเตือนงานใหม่ → **✅ รับเคส** → นำทาง / โทร → **🚤 ออกเดินทาง** → บันทึก + รูป → **✅ ช่วยแล้ว**
4. **ผู้ประสบภัย:** หน้าติดตามอัปเดตทีละขั้น (มีทีมรับ → กำลังช่วย → ปิดเคส)
5. **ศูนย์:** แท็บ **⚠️ ต้องจัดการ** · กรองสี/ชุด/พื้นที่ · กด 👥 ชุดว่าง ดูกระดานชุด + เคสที่ชุดยังไม่ตอบรับเกิน 10 นาที
6. **AI:** ส่งข้อความกำกวม → ผลลัพธ์บอก "↗ ส่งต่อ LLM" และ "🔒 ปิดบังก่อนส่ง: เบอร์ 1" → แก้ผล AI → ⚙️ จัดการระบบ → ดาวน์โหลดข้อมูลที่เจ้าหน้าที่แก้ (ใช้เทรนรอบหน้า)
7. **หน้าสาธารณะ `/public`:** ตัวเลขรายพื้นที่ แผนที่หยาบ ไม่มีข้อมูลส่วนตัว

ข้อควรรู้ตอนสาธิตบนมือถือผ่าน `http://IP`: ปุ่ม 📍 GPS ของเบราว์เซอร์ใช้ได้เฉพาะ https หรือ localhost — ถ้าต้องโชว์ GPS ให้เปิดผ่าน tunnel ที่เป็น https (เช่น `cloudflared tunnel --url http://localhost:5173`) หรือพิมพ์พิกัดในข้อความแทน · Windows Firewall ต้องอนุญาตพอร์ต 5173

### แชทบอท (`06_chat_assistant`)

- **จำเคสในแชท:** แจ้งเหตุแล้วบอทถามข้อมูลสำคัญที่ยังขาด**ทีละข้อ** (ตำแหน่ง → เบอร์ → จำนวนคน → ระดับน้ำ) พร้อมปุ่มตอบเร็ว คำตอบถัดไปเพิ่มเข้า**เคสเดิม** ไม่สร้างเคสซ้ำ · "ทีมมายัง" ตอบสถานะ ทีมที่รับ และสิ่งที่ยังขาด · "ปลอดภัยแล้ว" ถามยืนยันก่อนปิดเคส · "อีกบ้าน…" สร้างเคสใหม่ · เหตุวิกฤตระหว่างรอ (เช่น "ยายหมดสติแล้ว") เพิ่มเข้าเคสเดิมพร้อมขึ้นเบอร์ 1669
- **ไม่เดา:** ถ้าคำถามไม่ตรงกับคลังความรู้พอ บอทบอกว่าไม่มีข้อมูล แทนการตอบเรื่องอื่น · ตำแหน่งกลางของพื้นที่ไม่ถูกส่งเป็นพิกัดบ้าน
- **NLU:** ใช้กฎ regex จับ intent 11 แบบก่อน ถ้าความมั่นใจต่ำกว่า 0.6 จึงให้ LLM ช่วย (`/llm/json` ของ agent; เปิดด้วย `CHAT_USE_LLM=1`)
- **ข้อมูลสถานที่:** ชื่อ จุดที่ไป และเบอร์โทร มาจากตาราง `places` เท่านั้น LLM ไม่ได้แต่งขึ้น ข้อมูลตั้งต้น 9 จุดเป็น **ข้อมูลตัวอย่าง (สมมติ)** ต้องแทนด้วยข้อมูลจริงผ่าน `POST /api/places`
- **ความรู้ทั่วไป:** RAG แบบ BM25 ตัวอักษรคู่ อ่านจาก `kb/*.md` (เบอร์ฉุกเฉิน, วิธีขอความช่วยเหลือ, การบริจาค, ความปลอดภัย, สุขภาพ, คำถามการใช้ FloodLink/ข้อมูลส่วนตัว, เตรียมตัว-อพยพ, หลังน้ำลด) ไฟล์แบบ `## คำถาม / คำถามแบบอื่น` = FAQ แก้ไขไฟล์ได้เลย ทุกคำตอบแสดง "ที่มา" กำกับไว้
- **API:** `POST /api/chat {message, session_id, lat?, lng?}` · `GET/POST /api/places` · `GET /api/needs-summary`

```bash
curl -X POST localhost:8000/api/places -H "Content-Type: application/json" -d '{"id":"HUB-01","type":"donation_hub","name":"...","area":"คอหงส์","accepts":["water","food"],"short_of":["water"],"contact":"08x...","hours":"08:00-20:00"}'
```
type: `donation_hub` `kitchen` `shelter` `distribution` `medical` · item: `water food milk medicine hygiene clothes power sandbags boat`

```
ข้อความ ─► 02 API ─HTTP─► 03 Intake AI Agent
                              │

                              │       ├─ มั่นใจ ≥ threshold ─► ใช้คำตอบนี้

                              │              Gemini ─(ล่ม/โควตาหมด)─► Groq ─(ล่ม)─► ใช้คำตอบของโมเดลเรา (คำขอไม่หาย)
                              │              ตัวที่ล่มถูกพัก 60 วิ (circuit breaker) · คำตอบ LLM ถูกบันทึกเป็นข้อมูลเทรน
                              ▼
      02: ให้สีตามเกณฑ์ ปภ. (อธิบายเหตุผลได้) ─► รวมเคสซ้ำ / ปิดเคส / ปักหมุดจุดอันตราย ─► 01 Dashboard
```

**วงจรพัฒนาโมเดล (distillation loop)**

```
teacher_labels.jsonl  (คำตอบของ Gemini ทุกครั้งที่ถูกส่งต่อ)
   └─► python 04_flood_nlp_model/train.py --extra data/teacher_labels.jsonl
          └─► โมเดลเก่งขึ้น ─► ส่งต่อ Gemini น้อยลง ─► ประหยัด API และไม่ต้องพึ่ง API
```

### ใช้โมเดล WangchanBERTa (v2, เทรนจากข้อความจริง)

1. ดาวน์โหลด `floodwcb_model_rules.zip` จาก Google Drive (`MyDrive/floodlink_wcb/`, ได้จาก `apply_rules_colab.ipynb`)
2. แตกไฟล์ไว้ที่ `04_flood_nlp_model/artifacts/floodwcb_model/` (ต้องมี `model.pt`, `floodwcb_config.json`, ไฟล์ tokenizer)
3. `docker compose up --build agent` แล้วเปิด http://localhost:8001/health ต้องเห็น `"own_model_kind": "wcb"`

- `OWN_MODEL=auto` (ค่าเริ่มต้นใน `.env`): ถ้ามีโฟลเดอร์โมเดลใช้ WangchanBERTa ถ้าไม่มีกลับไปใช้ v1 เอง agent ไม่ล้ม
- สีของเคสยังมาจากกฎ ปภ. เหมือนเดิม โมเดลทำได้แค่ **ยกสีให้เร่งด่วนขึ้น** (`priority_hint`) เช่นเจอคำ "ทารก", "ตัวซีด" และเหตุผลบนการ์ดเคสจะขึ้นต้นด้วย `AI:` ให้เจ้าหน้าที่เห็น
- ใช้ CPU ประมาณ 0.1–0.4 วินาทีต่อข้อความ และ RAM ประมาณ 1.5 GB · ไม่อยากติดตั้ง torch: `docker compose build --build-arg WITH_WCB=0 agent`

## ผลวัด

วัดบน**ชุด hard 30 ข้อความ** (เขียนเองแบบอิสระ ไม่ได้ใช้เทรนหรือใช้ปรับโมเดล ใช้วัดเป็นครั้งสุดท้ายเท่านั้น)

| ตัวชี้วัด | Rules | โมเดลเรา v1 | **โมเดลเรา v1.1** | Hybrid (v1 + Gemini 3.5) |
|---|---|---|---|---|
| ระบุประเภทข้อความถูก | 66.7% | 80.0% | **93.3%** | 96.7% |
| ให้สีถูก | 36.8% | 63.2% | 63.2% | 84.2% |
| จับเคสแดงได้ | 55.6% | 66.7% | 55.6% | **88.9%** |
| needs F1 | 0.52 | 0.71 | **0.93** | 0.64 |
| ระบุฟิลด์ที่ขาดถูก | 31.6% | 94.7% | 89.5% | 89.5% |
| ส่งต่อ Gemini | – | – | – | 17/30 |

**v1.1 เพิ่มอะไร:**

- คลังคำพ้องความหมาย (`lexicon.py`) และการจัดการคำปฏิเสธ
- ข้อมูลเทรน 8,000 ข้อความที่หลากหลายขึ้น
- กฎความปลอดภัย `help_bias`: ถ้ามีสัญญาณว่าเป็นคำขอความช่วยเหลือ ให้ถือเป็นคำขอความช่วยเหลือไว้ก่อน
- ตัวดึงตัวเลขที่อ่าน "12 ชีวิต" และ "เกิดได้ 10 วัน" ได้

**ผลบนชุด dev 39 ข้อความ** (ใช้ระหว่างปรับ ตัวเลขจึงสูงเกินจริง): v1 ให้สีถูก 24/28 → v1.1 ได้ 28/28 และจับเคสแดงได้ 10/11 → 11/11

**ข้อสรุปที่ตรงไปตรงมา:**

1. v1.1 แยกประเภทข้อความและดึงสิ่งที่ต้องการได้ดีขึ้นมาก แต่**ยังจับกลุ่มเปราะบางที่ใช้คำที่ไม่เคยเห็นไม่ได้** เช่น "นอนอยู่กับที่" และ "ล้างไต" (ผมจงใจไม่ใส่คำในชุด hard ลงในคลังคำ เพื่อให้วัดผลได้ยุติธรรม) ตัวเลขการจับเคสแดงของโมเดลเราอย่างเดียวจึงไม่ดีขึ้น
2. ในเคสเหล่านี้ v1.1 **มั่นใจสูงทั้งที่ตอบผิด** จึงเพิ่มตัวกันใน Agent: ถ้ามีคำเกี่ยวกับสุขภาพทั่วไป (ป่วย, เลือด, ไต, พิการ, ลุก…) แต่ไม่พบกลุ่มเปราะบาง ให้ส่งต่อ Gemini ผลคือ**เคสแดงที่โมเดลเราพลาดถูกส่งต่อครบ 4/4** โดยส่งต่อแค่ 7/30 ข้อความ (v1 ส่งต่อ 17/30)
3. ยังไม่ได้รันคอลัมน์ hybrid กับ v1.1 จริง เพราะโควตา Gemini หมด ตัวเลขข้างบนเป็นของ v1 ต้องรันใหม่หลังโควตารีเซ็ต
4. ในชุดแม่แบบ 200 ข้อความ เคสแดง 2 เคสที่ยังพลาดเป็นเคสที่**ข้อความไม่ได้บอกข้อมูลนั้นเลย** เพราะตัวสร้างข้อมูลตัดข้อมูลบางส่วนออก แต่เฉลยยังเป็นของเคสเต็ม ไม่ใช่ความผิดของโมเดล

| ชุดข้อมูล | ส่งต่อ Gemini (v1.1 + ตัวกัน) | เคสแดงที่โมเดลเราพลาด → ถูกส่งต่อ |
|---|---|---|
| แม่แบบ 200 | 1 | 2 → 0 (ข้อความไม่ได้บอกข้อมูลนั้น) |
| hard 30 | 7 | 4 → **4** |
| dev 39 | 2 | 0 |

ดูข้อผิดทีละข้อได้ด้วย `python 05_evaluation/error_analysis.py --data <ไฟล์>`
